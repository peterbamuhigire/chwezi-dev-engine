# Implementation Plan: 18-Book Cross-Engine Kaizen Wave

**Date:** 2026-09-02  
**Design:** `docs/superpowers/specs/2026-09-02-18-book-cross-engine-kaizen-design.md`

## Phase 1 — Source and engine study record

1. Create the central wave ledger with all 18 supplied paths, provenance/accessibility status,
   durable independent synthesis, historical/currentness limits, and engine applicability.
2. Record the empty/404 prompt-engineering source as `NOT_ASSESSED`.
3. Record the official current-source ledger used to gate volatile claims, including Git,
   Bash/ShellCheck, HTTP RFCs, Spring Boot, Python, Google Search/LocalBusiness, W3C WCAG/WAI,
   and OWASP defensive guidance.
4. Mark inferred transfers separately from source-derived principles; do not store raw text.

## Phase 2 — Engine-specific adoption

1. Add one concise reference under each engine's existing Kaizen owner (or the Windows meta
   owner created in this wave).
2. Upgrade the ten existing Kaizen owner `SKILL.md` files with a link and a short discoverability
   contract that routes book-derived work to the new reference and Digital Research.
3. Create the Windows Kaizen owner using the engine's R0–R5 risk model, safe PowerShell mutation
   boundary, target/management-plane resolution, currentness gate, and native validation list.
4. Add the Windows skill to its catalogue/router/source map and a focused routing regression.
5. Correct the stale canonical path in `skills-web-dev/AGENTS.md` only where it refers to the
   current Digital Research checkout; leave historical records untouched.

## Phase 3 — Test-first verification

1. Before claiming completion, run structural checks for frontmatter, references, raw-text
   leakage, currentness markers, and Windows catalogue/routing registration.
2. Run every repository's native validators and tests in parallel where independent.
3. Run currentness/source-ingestion checks and verify that unavailable live/lab evidence remains
   `NOT_ASSESSED`.
4. Review the diff for scope creep, duplicate skills, unsafe shell/exploit material, copied text,
   and broken links.
5. Record changed/new counts, residual gaps, validation results, and the next re-audit date in
   the central ledger.

## Acceptance criteria

- All 18 source statuses are explicit; the unavailable prompt source produces no inferred claims.
- All 11 engines appear in the crosswalk and have a discoverable book-integration reference.
- The Windows Kaizen route is registered and its routing smoke test passes.
- Every Kaizen owner points to the canonical currentness gate and its engine-specific reference.
- No raw book text or cookbook exploit material is committed.
- Native validators pass, or their unavailable components are explicitly recorded as
  `NOT_ASSESSED`.
- Counts are evidence-backed: new skills, new references, and changed/upgraded existing skills
  are reported separately.
