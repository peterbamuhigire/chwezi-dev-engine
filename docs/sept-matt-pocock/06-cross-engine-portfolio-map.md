# Cross-Engine Portfolio Map

The source ideas are cross-cutting, but ownership must stay singular. This map tells the Kaizen
agent where to apply each pattern and where only a pointer belongs.

## Portfolio-wide capabilities

| Pattern | Canonical owner | Engines that consume it | Consumption rule |
| --- | --- | --- | --- |
| Skill attention and invocation doctrine | `skills-web-dev/skill-writing` | All engines | Link from routers/authoring skills; do not copy full doctrine |
| Decision-tree frontier questioning | SRS | Business plan, proposal, social, design, website, engineering | Domain wrapper adds questions and outputs only |
| Domain language and decision records | SRS plus engineering architecture seam | All product-producing engines | SRS owns stakeholder meaning; engineering owns implementation decisions |
| Tracer-bullet work graph | `skills-web-dev` | Website, app, admin, infrastructure, proposal delivery | Each engine maps "slice" to its own deliverable unit |
| Systematic diagnosis | `skills-web-dev` for software; admin engines for hosts | Website, Linux, Windows, mobile, AI | Share evidence-loop doctrine; keep domain probes local |
| Pointer-rich handoff | Coordination control plane | All engines | One handoff schema, domain evidence linked by path |
| Explicit/implicit invocation policy | Coordination plus runtime adapters | All engines | Semantic state is canonical; host syntax is adapter-owned |
| Lifecycle buckets and promotion gate | Coordination package | All engines | Experimental content must not consume active runtime budget |

## SRS engine

Adopt:

- Design-tree questioning with frontier rounds.
- Facts-versus-stakeholder-decisions separation.
- Shared-understanding confirmation before requirements are baselined.
- Domain glossary and ADR linkage.
- Synthesise-only mode when the conversation is already sufficient.
- Tracer-bullet implementation handoff with explicit requirement links.

Do not import `to-spec` as a competing skill. SRS remains the canonical specification owner.

## Business-plan engine

Adopt:

- Frontier interviews for strategic assumptions and unresolved decisions.
- Expert questionnaires for customer, market, operations, and finance evidence.
- Decision maps for plans too large for one session.
- Pointer-rich handoffs that link the financial model, sources, assumptions, and review state.

Finance assumptions still route to Chwezi accounting doctrine; current market facts route to Digital
Research.

## Website engine

Adopt:

- Throwaway prototypes that answer one conversion, IA, responsive, or interaction question.
- Tracer-bullet journeys from entry to task/conversion, including failure and consent states.
- Tight browser feedback loops for rendering and performance regressions.
- Two-axis review: brief/spec fidelity and implementation/launch standards.

Visual choices remain owned by the design engine. Prototype reports must use the project's authored
visual system and real content, not the source's generic Tailwind/CDN scaffold.

## Social-media engine

Adapt the in-progress writing trilogy as a gated reference sequence:

```text
fragments (explore) -> beats (ground and order) -> shape (exploit and draft)
```

Add campaign evidence, source provenance, brand voice, platform constraints, approval, moderation,
and measurement. Do not promote the three source beta skills as-is.

## Linux and Windows administration engines

Adopt:

- Tight diagnosis loops with exact target, before state, symptom oracle, and recovery.
- Human-operation wizards for dashboard, credential, hybrid, or physical steps.
- Work graphs for multi-host changes and dependency-aware maintenance windows.
- Pointer-rich handoff with target identity, owner, commands, result, rollback, and residual state.

Use PowerShell and Bash implementations behind one capability-neutral contract. Never treat a regex
command blocker as the security boundary.

## Proposal engine

Adopt:

- Expert questionnaires that grill the send rather than invent client knowledge.
- Two-axis review: solicitation compliance and persuasive/evidence quality.
- Work graphs for multi-workstream submission packages.
- Triage state machine for clarifications, evidence requests, owner review, and release blockers.

Existing bid red-team and delivery-QC gates remain stronger than the source review skill.

## Accounting doctrine

Adopt carefully:

- Domain glossary with approved accounting terms and rejected synonyms.
- Decision records for policy choices, estimates, materiality, and system treatments.
- Tight diagnosis loops for reconciliation differences and posting defects.
- Expert questionnaires for evidence held by controllers, auditors, tax advisers, or operations.

Do not let generic domain-modelling language override IFRS, IAS, tax, ledger, control, or statutory
definitions.

## Design engine

Adopt:

- Design-it-twice as independently framed alternatives followed by synthesis.
- Prototype-as-primary-source, with real content and cleanup.
- Decision frontier for design briefs and critique.
- Explicit invocation/lifecycle metadata for high-cognitive-load design operations.

Reject the source HTML report's generic `font-sans`, Tailwind CDN, and default component styling.
The design engine's own typography, colour, layout, accessibility, asset, and render gates prevail.

## Digital Research Engine

The source `research` skill is too thin to replace this engine. Borrow only:

- bounded background-agent brief;
- one durable cited output path;
- primary-source ownership language;
- continued orchestration while independent reading proceeds.

Keep Digital Research source evaluation, verification, contradiction handling, freshness, support
status, claim maps, and citation audit.

## Political essay engine

This private engine may adapt fragments -> beats -> shape, frontier questioning, domain vocabulary,
and expert questionnaires. It remains private and must never be added to public catalogues or
published through this Kaizen programme.

## Coordination package

Add portfolio-level validators for:

- active versus experimental/deprecated/reference lifecycle;
- semantic invocation state and per-runtime adapter agreement;
- promoted-set manifest accuracy;
- pointer existence and ownership;
- aggregate metadata budgets;
- evidence declarations and `NOT ASSESSED` propagation;
- handoff schema completeness;
- currentness review dates.
